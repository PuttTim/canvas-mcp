# canvas-mcp — Implementation Plan

A TypeScript [Model Context Protocol](https://modelcontextprotocol.io) server for
[Canvas LMS](https://www.instructure.com/canvas), validated against Canvas's published
API spec, with a curated, safety-annotated tool surface.

**v1 scope: students.** A student brings their own Canvas instance URL and a personal
access token, and gets a wide set of read and self-service write tools. Teacher toolsets
follow in a later phase; admin tooling is out of scope.

**Primary deployment target: Cloudflare Workers** (KV for grants, one Durable Object for
per-token rate-limit state). Local stdio and plain Node HTTP run through the same adapter
layer but are not the priority.

Inspiration: [jjuanrivvera/canvas-cli](https://github.com/jjuanrivvera/canvas-cli) (Go).
We borrow its spec-driven architecture, wide endpoint coverage, and safety model, but ship
as a Workers-first TypeScript server instead of a compiled CLI.

## Decisions (2026-09-19)

| # | Decision |
|---|---|
| Instances | Bring-your-own. The student supplies their institution's Canvas URL. |
| Auth | Pasted personal access tokens. No Canvas OAuth2 developer keys in v1. |
| Users | Students first; teacher toolsets later; no admin. |
| Tool surface | Curated toolsets, wide scope (canvas-cli breadth for student-reachable endpoints), plus a spec-validated generic request tool. |
| Destructive ops | Included, annotated per the MCP spec (`destructiveHint`), gated behind an opt-in. |
| Test instance | None. Mocks and recorded fixtures only. |
| Spec source | Bootstrap from the live Swagger 1.2 snapshot now. Swap to the OpenAPI 3 file generated by canvas-lms's `rake doc:openapi` later (it boots Rails and needs a DB, so it's a dockerised, manual step). |
| Name / license / account | `canvas-mcp`, MIT, Cloudflare account `putttimmanee`. |

## 1. Goals and non-goals

### Goals

1. **Cloudflare-first, adapter-based.** One `buildServer(ctx)` core; thin adapters for
   Workers (primary), Node HTTP, and stdio. No Cloudflare-specific code in tools or the
   Canvas client.
2. **Spec-driven correctness.** Every Canvas path the server calls is validated in CI
   against a committed spec manifest. Wrong paths fail the build.
3. **A tool surface an LLM can actually use.** Curated, well-described tools grouped into
   toolsets, wide enough to cover what a student can do in Canvas.
4. **Safe by default.** MCP tool annotations, a read-only mode, destructive tools behind
   an opt-in, `dry_run` on writes, compact responses.
5. **Multi-tenant.** One hosted deployment serves many students across many Canvas
   instances; a token is never shared between requests.

### Non-goals (v1)

- Teacher/admin workflows: grading, enrollment management, course creation, SIS, reports,
  masquerading. (Teacher toolsets are Phase 2; admin is not planned.)
- Canvas OAuth2 developer-key flow.
- LTI, JWT minting, plagiarism-platform APIs.
- REPL, table/CSV output, shell completion.

## 2. Facts that shape the design

| Topic | What Canvas actually does | Consequence |
|---|---|---|
| Spec format | Every Canvas host serves **Swagger 1.2** at `/doc/api/api-docs.json` plus 144 per-resource files (1,086 endpoints, with models). An **OpenAPI 3** file exists only via `bundle exec rake doc:openapi` inside canvas-lms, which boots Rails and requires a database; Instructure does not host it. | Commit a slimmed manifest derived from Swagger 1.2 now. Keep the derive step format-agnostic so the OpenAPI 3 file can replace the source later without touching consumers. |
| Spec hosting | `canvas.instructure.com` IP-blocks datacenter traffic; `learn.canvas.net` serves the same docs. | `spec:sync` takes a configurable host; CI never fetches. |
| Auth | `Authorization: Bearer <token>`. Students can generate personal access tokens under Account → Settings. Each token has its own rate-limit quota. Tokens inherit the user's permissions, so a student token simply can't reach teacher endpoints. | Token + base URL collected once at consent time, stored encrypted, sent as bearer on every Canvas call. |
| Pagination | `Link` header, `rel="current|next|prev|first|last"`, opaque absolute URLs. `per_page` up to ~100. `last` may be omitted. | Client follows `next`; tools expose `page_url` cursor and bounded `max_pages`. |
| Throttling | Leaky bucket per token. `X-Rate-Limit-Remaining` and `X-Request-Cost` headers. Exhaustion is **403 "Rate Limit Exceeded"**. Parallel requests pay an upfront penalty. | Adaptive limiter keyed on token. Workers isolates don't share memory, so limiter state lives in a **Durable Object per token hash**. |
| Param encoding | Rails brackets: `include[]=a&include[]=b`, `submission[body]=…`. Errors: `{ "errors": [{ "message": … }] }`. | Dedicated encoder and error normaliser. |
| Payload size | Objects are large; submissions embed users, rubrics, comments. | Trimmed projections by default, `verbose` escape hatch. |
| File uploads | Three-step: POST for upload params → multipart POST → confirm. Students upload to their own files area and to assignment submissions. | Dedicated `files_upload` and `submissions_upload_file`. |
| MCP on Workers | Spec 2026-07-28 made MCP stateless. Cloudflare deprecated `McpAgent` in favour of `createMcpHandler` (`agents/mcp/server`), which builds a fresh server per request. | No DO for the protocol. Per-request `McpServer` factory receives `authInfo` → tenant context. |
| MCP client auth | Claude, ChatGPT, and most remote-connector UIs speak OAuth to the MCP server (dynamic client registration + PKCE). They generally can't set custom headers. | Even with pasted Canvas tokens, the **MCP-facing side is OAuth** via `@cloudflare/workers-oauth-provider`. Our "consent page" is where the student pastes URL + token. |

## 3. Stack

| Concern | Choice |
|---|---|
| Language / runtime | TypeScript 5.x; Workers runtime first, Node ≥ 22 and Bun second. Web-standard `fetch` everywhere. |
| MCP SDK | `@modelcontextprotocol/server` 2.0.0 (spec 2026-07-28); `@modelcontextprotocol/node` for the Node adapter; stdio transport from the same family. |
| Workers glue | `agents` (`createMcpHandler`), `@cloudflare/workers-oauth-provider`, `wrangler`. |

| Tests | Vitest + `@cloudflare/vitest-pool-workers` + `msw`. Fixtures hand-built from spec model examples. |
| Lint / format | Biome. |
| CI | GitHub Actions: typecheck, lint, test, spec-contract, `wrangler deploy` on tag, `npm publish` for the local adapter. |

### 4.2 Adapter contract

```ts
export interface ServerContext {
  canvas: CanvasClient;             // one base URL + one token
  toolsets: Set<Toolset>;
  readOnly: boolean;
  allowDestructive: boolean;
  identity: { userId: number; name: string; baseUrl: string };
}
export function buildServer(ctx: ServerContext): McpServer;
```

- **Workers:** `createMcpHandler((authInfo, env) => buildServer(ctxFrom(authInfo, env)))`
  inside `OAuthProvider`. Grant props hold `{ baseUrl, sealedToken, userId, name, scopes }`.
- **Node:** same factory; token from env (single-tenant) or bearer passthrough with
  `X-Canvas-Base-URL` restricted to an allowlist.
- **Stdio:** `CANVAS_BASE_URL` + `CANVAS_TOKEN`, or a named instance from
  `~/.config/canvas-mcp/config.json`.

### 4.3 Consent flow (Workers)

1. MCP client starts OAuth against our Worker (DCR + PKCE handled by the provider).
2. Provider routes to `consent.ts`: a small HTML form asking for **Canvas URL** and
   **access token**, plus checkboxes for scopes: `write` (default on) and `destructive`
   (default off). Links to Canvas's "how to generate a token" page.
3. On submit, server-side: normalise URL to `https://<host>`, reject non-HTTPS and
   private/loopback hosts (SSRF guard), call `GET /api/v1/users/self` with the token.
   On success, seal the token with AES-GCM (key = Worker secret), store grant props,
   complete the authorization.
4. Every later request: provider validates the MCP access token, hands `authInfo.props`
   to the factory, which unseals the Canvas token and builds a `CanvasClient`.
5. Revocation: provider's standard revoke endpoint deletes the grant; the Canvas token
   itself is never stored unencrypted and never logged.

### 4.4 Client core

- `CanvasClient({ baseUrl, tokenSource, throttleStore?, fetch? })`.
- `request<T>(method, path, { query?, body?, formData? })` → `{ data, links, cost, remaining }`.
- `paginate()` async iterator; `collect(maxPages)`.
- Throttle tiers on `X-Rate-Limit-Remaining` (>50 % normal, 20–50 % slow, <20 % serialise);
  `MemoryThrottleStore` locally, `DurableObjectThrottleStore` on Workers. Retries
  403-rate-limit / 429 / 502-504 with jittered backoff, honouring `Retry-After`.
- Errors: `CanvasError { status, messages[], path }`; 401 → "token invalid or revoked,
  reconnect", 403 → "your account can't access this", 404 → "not found".

### 4.6 Safety model

- `readOnly` → only `read` tools registered.
- `allowDestructive` → required for `irreversible` tools. On Workers it is the `destructive`
  consent scope; locally the `--allow-destructive` flag / env.
- Every write supports `dry_run: true` returning the exact request.
- `submissions_submit` and `quizzes_submission_complete` have real academic consequences.
  They are **implemented but not registered by default**: they belong to a `submit`
  feature flag (`CANVAS_MCP_FEATURES=submit` locally, a `submit` consent scope on Workers).
  When enabled they echo the exact payload and ask for confirmation via elicitation when
  the client supports it.
- Published exact tool names in `docs/agent-safety.md` for host deny/ask rules.

### 4.7 Responses

`structuredContent` (typed) plus a one-line text summary. Projections keep ids, names,
dates, states, points, URLs; `verbose: true` returns the raw object. HTML → Markdown by
default. Lists return `next_page_url`, never silent truncation. Tool defaults:
`per_page` 25, `max_pages` 1.

### 4.8 Spec pipeline

1. `pnpm spec:sync --host https://learn.canvas.net` → `spec/swagger12/`.
2. `pnpm spec:derive` → `spec/endpoints.json`, `spec/models.json` (sorted, stable).
   The deriver has a source interface so an OpenAPI 3 loader can be dropped in later.
3. `pnpm gen:types` → `src/canvas/types.gen.ts`.
4. `test/spec-contract.test.ts` scans services for path templates and asserts each
   `(method, path)` exists in `endpoints.json`. Network-free, runs in `pnpm test`.
5. `pnpm spec:coverage` reports implemented vs documented per resource.

- Exit: `wrangler dev` serves `/mcp`; Inspector lists courses with a pasted token;
  stdio does the same.

### M1 — Consent flow and multi-tenancy (implemented 2026-09-19, live at https://canvas-mcp.putt.workers.dev)
- `workers-oauth-provider` integration, consent page (URL + token + scopes), token
  validation, AES-GCM sealing, KV grants, SSRF guard.
- Durable Object throttle store.
- Miniflare tests for consent, revoke, per-request factory.
- Deploy to `putttimmanee` account.
- Exit: Claude web "Add custom connector" → consent → lists courses. Two students on
  different instances work from one deployment.
- Verification: mocked OAuth/PKCE flow and live discovery passed. The real Claude login,
  two-student live flow, and grant revocation are not yet verified by the current tests.

### M2 — Student toolsets, breadth (implemented locally 2026-09-19; not deployed)
- `assignments`, `submissions`, `grades`, `modules`, `pages`, `announcements`,
  `discussions`, `files`, `calendar`, `planner`, `conversations`.
- Projections, HTML→Markdown, `dry_run`, fixtures per tool.
- Exit: an agent can answer "what's due this week", read an assignment, submit a text
  entry, reply to a discussion, and read inbox messages.
- Implementation: 98 new tools (117 total), with fixtures for every tool, projections,
  bounded pagination and write previews. The exit workflow passes through an MCP SDK
  client against mocked Canvas; protected Workers tests cover planner reads and submit
  previews after OAuth consent, including separate Canvas instances.
- All writes, including M0 tools, support `dry_run`. Submission is hidden without the
  `submit` scope/feature and requires explicit `confirmed: true` for execution. Elicitation
  remains M3 work. No real academic work or messages were submitted while testing.
- Uploads accept bounded base64 (5 MiB decoded) and perform the three-step Canvas flow;
  they do not submit the assignment. This is a bounded-buffer implementation, not the
  unbounded streaming upload proposed above. Larger files use Canvas's own upload UI.
- Student endpoint interpretations: `overrides_for_me` returns Canvas's effective personal
  assignment dates; `submission_summary_mine` summarizes only the current student's
  fetched submissions. Subscribed topics and reserved appointment groups are filtered
  after pagination and preserve continuation cursors.
- Real institution behavior and a real Claude connector login remain unverified. Production
  continues to serve M1 until M2 is deployed.

### M3 — Remaining toolsets, safety hardening
- `quizzes`, `groups`, `people`, `outcomes`, `bookmarks`, `api`.
- Read-only mode, `destructive` scope, elicitation on `submit`, agent-safety doc,
  coverage report.

### M4 — Secondary adapters, release
- Node adapter + Dockerfile; `npm publish` (`npx canvas-mcp stdio`).
- Resources (`canvas://me`, `canvas://courses/{id}`) and prompts (`week_ahead`,
  `course_overview`).
- README, deploy docs, CHANGELOG, MCP registry listing.

### Phase 2 (later) — Teachers
- `teaching` toolsets: grading, submissions for all students, assignment/page/module CRUD,
  enrollments, sections, rubrics, gradebook history. Same `defineTool` contract, separate
  files, gated by a `teacher` consent scope.
- Optional Canvas OAuth2 developer-key flow for institutions that want it.
- Swap spec source to the OpenAPI 3 file via dockerised `rake doc:openapi`.

## 7. Risks

- **New SDKs.** `@modelcontextprotocol/server` 2.0.0 and `createMcpHandler` are months
  old. Confined to `src/adapters/` so a fallback to SDK 1.30 is a one-file change.
- **Tokens at rest.** Student tokens are long-lived and powerful. AES-GCM with a Worker
  secret, never logged, revoke path tested, consent page explains how to revoke in Canvas.
- **No test instance.** Fixtures are hand-built from spec examples, so behavioural drift
  in Canvas won't be caught until a real user hits it. Mitigation: `doctor` tool that
  exercises a few read endpoints; encourage a Free-for-Teacher account later.
- **Response size / Workers limits.** CPU and subrequest caps bound `max_pages`; uploads
  stream rather than buffer.
- **Student write endpoints vary by course settings.** Page edits, discussion posting,
  and group joins may 401/403 depending on course config; errors must say so plainly.

## 8. Remaining open points

None blocking.
- `submissions_submit` and `quizzes_submission_complete`: implemented, hidden behind the
  `submit` feature flag (decided 2026-09-19).
- The `api` toolset is off by default and `canvas_request` for non-GET is `irreversible`.
